## 1. Общая картина

Обе работы — это **одно и то же ядро** (математические модели объектов
управления из ЛР №1 + модуль анализа устойчивости), вокруг которого надстроены
две разные программы:

```
                 ┌──────────────────────────────────────────┐
                 │  ЯДРО (общее для ЛР2 и ЛР3)              │
                 │  Model.h, Model1_6, Model2_8, Model3_10  │
                 │  StabilityAnalyzer                       │
                 └───────────────┬──────────────────────────┘
                                 │
          ┌──────────────────────┴──────────────────────┐
          │                                             │
   ЛР №2 (task_02_github)                        ЛР №3 (task_03_github)
   + InputSignal (генератор U)                   + PIDController (регулятор)
   + Simulation (движок прогона)                 + замкнутый контур в main.cpp
   = «прогон модели при заданном входе»          = «ПИД управляет объектом»
```

Логика разделена на **три слоя**, и это ключ к пониманию структуры:

| Слой | Что это | Файлы | Зачем отдельно |
|---|---|---|---|
| **Модели** | математика объектов | `Model*.h/.cpp` | объект управления можно менять, не трогая остальное |
| **Движок** | «как считать во времени» | `Simulation.*` (ЛР2), `PIDController.h` (ЛР3) | алгоритм расчёта отделён от модели |
| **Оболочка** | ввод/вывод, меню, файлы | `main.cpp` | логику можно тестировать без консоли |

Такое разделение нужно ровно для одной практической цели: **логику можно
проверять тестами**, не запуская программу и не вводя числа руками.

## 2. Общие понятия

### 2.1. Дискретная модель

Объект описывается не дифференциальным уравнением в непрерывном времени, а
**разностным** — значение на следующем такте `t+1` вычисляется по значениям на
прошлых тактах. Такт — это шаг дискретного времени `τ = 0, 1, 2, …`.

Общий интерфейс модели (`Model.h`) требует одну функцию:

```
y(t+1) = calculateNext(y(t), y(t-1), y(t-2), u(t), dt)
```

* `y` — регулируемая величина (то, что наблюдаем),
* `u` — вход / управление,
* `dt` — шаг интегрирования (нужен только модели 3.10, остальные его игнорируют),
* `y`, `yPrev`, `yPrev2` — текущее, предыдущее и пред-предыдущее значения.

### 2.2. Полиморфизм (виртуальные функции)

`Model` — **абстрактный базовый класс**: у него нет реализации
`calculateNext`, есть только объявление `= 0`. Конкретные модели
(`Model1_6`, `Model2_8`, `Model3_10`) наследуют его и **переопределяют**
(`override`) метод. Благодаря этому функция `simulate(const Model&, …)`
принимает любую модель и вызывает «правильную» реализацию во время работы
программы. Именно поэтому движок симуляции не знает, с какой моделью работает.

### 2.3. Google Test и unit-тесты

**Юнит-тест** (модульный тест) — маленькая программа, которая вызывает одну
функцию и сравнивает результат с заранее известным эталоном. Если результат не
совпал — тест падает и печатает, что именно не совпало.

Минимальные макросы Google Test, которые встречаются в коде:

| Макрос | Смысл |
|---|---|
| `TEST(Набор, ИмяТеста)` | объявляет один тест |
| `EXPECT_EQ / EXPECT_NEAR / EXPECT_DOUBLE_EQ` | проверка; при провале тест **продолжается** |
| `EXPECT_TRUE / EXPECT_FALSE / EXPECT_LT / EXPECT_GT` | проверки-утверждения |
| `ASSERT_*` | то же, но при провале тест **прерывается** (нужно, если дальше нельзя) |
| `SCOPED_TRACE("текст")` | добавляет к сообщению об ошибке контекст (какой случай упал) |
| `TEST_P` + `INSTANTIATE_TEST_SUITE_P` | параметризованный тест: один код, много наборов данных |
| `NiceMock<T>` | «мок» (заглушка) объекта, который не ругается на лишние вызовы |
| `ON_CALL` / `EXPECT_CALL` | задать поведение мока / ожидать вызов |

**Зачем тесты вообще нужны:**

1. Доказывают, что формулы реализованы верно (эталоны посчитаны вручную).
2. Ловят регрессии: после любой правки кода тесты за секунды покажут, что
   сломалось.
3. Это защита от «ошибка в формуле» — самая частая проблема в расчётах: код
   работает, но считает не то.
4. Тесты — это документация: по ним видно, какую формулу и с какими граничными
   случаями гарантирует каждая функция.

* **`Model.h`** — единый «разъём». Пока все модели умеют `calculateNext` и

* **`Model1_6/2_8/3_10`** — три разных объекта из ЛР №1 (линейный, нелинейный,

* **`Simulation.h/.cpp`** — «как крутить цикл по тактам и хранить историю».
  Здесь же определён интерфейс источника входа `IInputSource` — благодаря нему
  в тестах вход можно подменить на любой (в том числе google-mock).
* **`StabilityAnalyzer.h/.cpp`** — математика устойчивости: поиск корней
  полинома, критерий Шура, формирование отчёта/предупреждения. Это
  самостоятельный модуль (его же потом подключает ЛР №3).
* **`main.cpp`** — «оболочка»: диалог с пользователем. Здесь нет математики —
  только ввод, вывод таблицы, запись CSV и запуск `plot.py`.
* **`plot.py`** — строит картинку по `results.csv`. Отдельно, потому что
  графикой занимается Python/matplotlib, а не C++.
* **`test/`** — отдельный проект-исполняемый файл `otis_tests.exe`; тесты
  собираются отдельно от программы, чтобы их можно было гонять без неё.
* **`CMakeLists.txt`** — описывает, из каких `.cpp` собирается библиотека
  `otis_core`, программа `otis_task_02` и тесты `otis_tests`.
* **`run_tests.bat`** — автоматизация: найти Visual Studio, сконфигурировать,
  собрать, прогнать `ctest`, посчитать покрытие.

## 4. ЛР №2: разбор кода

### 4.1. `src/Model.h`

```cpp
#pragma once                      // защита от двойного включения заголовка
class Model
{
public:
    virtual ~Model() = default;   // виртуальный деструктор
    virtual double calculateNext(double y, double yPrev, double yPrev2,
                                 double u, double dt) const = 0;  // чистая виртуальная
    virtual const char* getName() const = 0;
};
```

* `#pragma once` — компилятор включает файл не более одного раза за сборку.
* `virtual ~Model() = default` — **обязательно** виртуальный деструктор:
  объекты моделей удаляются через указатель на базовый класс
  (`std::unique_ptr<Model>`), и без `virtual` не вызвался бы деструктор
  наследника.
* `= 0` в конце `calculateNext` делает метод **чисто виртуальным**: у базового
  класса нет тела, класс становится абстрактным — создать `Model` напрямую
  нельзя, только наследника.
* `const` в конце — метод не меняет объект.
* Итого `Model` — это «контракт»: любой объект, умеющий эти две функции, — модель.

### 4.2. `src/Model1_6.h` / `Model1_6.cpp`

Заголовок:

```cpp
class Model1_6 final : public Model
{
private:
    double a1, a2, a3, b;                      // коэффициенты
public:
    Model1_6(double a1, double a2, double a3, double b);   // конструктор
    double calculateNext(...) const override;  // реализация контракта
    const char* getName() const override;
    double getA1() const; double getA2() const;   // доступ к коэффициентам
    double getA3() const; double getB()  const;
};
```

* `final` — от этой модели нельзя наследоваться (защита от случайного
  «ошибки по наследству»).
* `: public Model` — наследование публичное: снаружи видно, что это `Model`.
* Геттеры `getA1()…getB()` добавлены специально, чтобы модуль устойчивости и
  тесты могли прочитать коэффициенты, не «залезая» внутрь объекта.

Реализация (`Model1_6.cpp`):

```cpp
Model1_6::Model1_6(double a1, double a2, double a3, double b)
    : a1(a1), a2(a2), a3(a3), b(b) {}      // список инициализации

double Model1_6::calculateNext(double y, double yPrev, double yPrev2,
                               double u, double /*dt*/) const
{
    return a1 * y + a2 * yPrev + a3 * yPrev2 + b * u;
}
```

* `: a1(a1), …` — инициализация полей значениями параметров (имя поля = имя
  параметра, поэтому пишем `a1(a1)`).
* `/*dt*/` — безымянный параметр: показываем, что `dt` модели не нужен
  (у неё нет интегратора), но он должен быть в сигнатуре, чтобы совпасть с
  контрактом `Model`.
* Строка `return a1*y + a2*yPrev + a3*yPrev2 + b*u;` — это и есть вся модель
  1.6: линейная авторегрессия 3-го порядка плюс вклад входа.

### 4.3. `src/Model2_8.h` / `Model2_8.cpp`

```cpp
double Model2_8::calculateNext(double y, double yPrev, double /*yPrev2*/,
                               double u, double /*dt*/) const
{
    return a * y * (1.0 - y) + b * u + c * std::sin(yPrev * u);
}
```

* Член `a*y*(1-y)` — «логистическая карта», классический источник
  нелинейности/хаоса.
* `c*sin(yPrev*u)` — нелинейное sin-возмущение; `yPrev2` и `dt` не нужны.
* Файл подключает `<cmath>` — ради `std::sin`.

### 4.4. `src/Model3_10.h` / `Model3_10.cpp`

```cpp
double Model3_10::calculateNext(double y, double /*yPrev*/, double /*yPrev2*/,
                                double u, double dt) const
{
    return y + dt * (-a * y + b + u);
}
```

* Здесь модель задана **дифференциальным уравнением** `dy/dt = -a*y + b + u`.
  Метод Эйлера: `y(t+1) = y(t) + dt * f(y,u)`.
* `-a*y` — стремление к равновесию, `b` — постоянное смещение, `u` — управление.
* Уравнение 1-го порядка, поэтому `yPrev`, `yPrev2` — не используются.
* Именно у этой модели `dt` реально влияет на результат (в отличие от 1.6/2.8).

### 4.5. `src/InputSignal.h` / `InputSignal.cpp`

```cpp
enum class SignalType { Step = 1, Impulse = 2, Harmonic = 3 };
double getInput(SignalType type, int tau, double amplitude);
```

`enum class` — «строгий» перечисляемый тип: значения не превращаются молча в
числа, их нужно писать как `SignalType::Step`. Числа `1/2/3` нужны для меню.

```cpp
double getInput(SignalType type, int tau, double amplitude)
{
    switch (type)
    {
    case SignalType::Step:     return amplitude;                        // u = A
    case SignalType::Impulse:  return (tau == 0) ? amplitude : 0.0;     // только в 0
    case SignalType::Harmonic: return amplitude * std::sin(tau);        // u = A*sin(t)
    }
    return 0.0;      // недостижимо при корректном type; ветка «по умолчанию»
}
```

* Ступенька: постоянное воздействие `A`.
* Импульс: короткий «толчок» амплитуды `A` только в момент `τ=0`.
* Гармоника: синусоида с амплитудой `A` и периодом `2π`.
* Последний `return 0.0` делает функцию безопасной при недопустимом `type`.

### 4.6. `src/Simulation.h` / `Simulation.cpp`

Заголовок объявляет:

```cpp
struct SimStep { int tau = 0; double u = 0.0; double y = 0.0; };  // строка результата
struct SimulationConfig { int steps = 10; double y0 = 0.0; double dt = 1.0; };
```

* `SimStep` — одна строка таблицы: номер такта, вход, выход.
* `SimulationConfig` — параметры прогона с значениями по умолчанию.
* Значения по умолчанию (`= 10`, `= 0.0`, `= 1.0`) — чтобы можно было писать
  `SimulationConfig{n, y0, 1.0}` и не заполнять всё вручную.

Интерфейс источника входа:

```cpp
class IInputSource
{
public:
    virtual ~IInputSource() = default;
    virtual double valueAt(int tau) const = 0;
};
```

Зачем интерфейс, а не просто `getInput`? Потому что в тестах нужно **подменить**
вход: задать ступеньку, импульс, произвольную функцию или мок. Реализации:

* `SignalInputSource` — обёртка над `getInput(type, …)`;
* `CallableInputSource` — обёртка над `std::function<double(int)>`
  (произвольная функция `u(τ)`);
* `MockInputSource` — в тестах (наследник `IInputSource`, см. раздел 6).

Движок:

```cpp
std::vector<SimStep> simulate(const Model& model,
                              const SimulationConfig& config,
                              const IInputSource& input)
{
    const int steps = config.steps < 0 ? 0 : config.steps;   // защита от отрицательного n
    std::vector<SimStep> rows;
    rows.reserve(static_cast<std::size_t>(steps) + 1);

    double y = config.y0, yPrev = config.y0, yPrev2 = config.y0;

    rows.push_back({0, input.valueAt(0), y});                // строка τ=0 — начальное состояние

    for (int tau = 0; tau < steps; ++tau)
    {
        const double u = input.valueAt(tau);
        const double nextY = model.calculateNext(y, yPrev, yPrev2, u, config.dt);

        yPrev2 = yPrev;   // сдвиг истории: важно делать именно в таком порядке
        yPrev  = y;
        y        = nextY;

        rows.push_back({tau + 1, input.valueAt(tau + 1), y});
    }
    return rows;
}
```

Построчно:

* `steps = … < 0 ? 0 : steps` — отрицательное число шагов трактуется как 0
  (тест `Simulation.ZeroAndNegativeSteps` это проверяет).
* `rows.reserve(steps+1)` — заранее выделяет память: строк ровно `steps+1`
  (включая начальную).
* `y, yPrev, yPrev2 = y0` — до старта вся «история» равна начальному условию.
* `rows.push_back({0, …})` — первая строка: такт 0, вход `u(0)`, выход `y0`.
* В цикле порядок сдвига **сначала `yPrev2 = yPrev`, потом `yPrev = y`, и только
  затем `y = nextY`** — если перепутать, потеряется одно из прошлых значений.
* `input.valueAt(tau+1)` в строке результата `τ+1` — записывается вход,
  который будет подан на следующем такте.

### 4.7. `src/StabilityAnalyzer.h` / `StabilityAnalyzer.cpp`

Это самый «математический» модуль, разбор — в разделах 5 и 6. Здесь — карта API:

```cpp
enum class StabilityVerdict { Stable, Marginal, Unstable };

struct StabilityReport {
    std::string modelName;
    std::vector<double> coefficients;          // коэффициенты полинома
    std::vector<std::complex<double>> roots;   // корни
    double spectralRadius = 0.0;               // max |z|
    StabilityVerdict verdict = StabilityVerdict::Stable;
};

class StabilityAnalyzer {
public:
    static std::vector<std::complex<double>> findRoots(const std::vector<double>&);
    static StabilityVerdict schurVerdict(const std::vector<double>&);
    static bool isStable(const std::vector<double>&);
    static bool needsWarning(const StabilityReport&);
    static double spectralRadius(const std::vector<std::complex<double>>&);
    static StabilityReport analyzeModel1_6(double a1, double a2, double a3);
    static std::vector<double> characteristicPolynomial1_6(double a1,double a2,double a3);
    static bool isMarginallyStable(const std::vector<double>&);
    static std::string describe(const StabilityReport&);
    static std::string warningText(const StabilityReport&);
    static bool printWarningIfNeeded(const StabilityReport&, std::ostream&);
};
```

* Все методы `static` — модуль не хранит состояние, это набор функций.
* `StabilityReport` — «пакет результатов»: имя модели, коэффициенты, корни,

## 5. Теория устойчивости

Это ядро ЛР №2 и одна из главных тем для защиты.

### 5.1. Что такое устойчивость на пальцах

Система **устойчива**, если после отклонения (от внешнего толчка или отличного
от равновесия начального состояния) она **сама возвращается** к равновесию, а не
уходит в бесконечность и не начинает раскачиваться с нарастающей амплитудой.

* Устойчива: «маятник с трением» — колебания затухают.
* Неустойчива: «маятник с отрицательным трением» — амплитуда растёт, значения
  расходятся; численное решение теряет смысл.
* Граница устойчивости: колебания не затухают и не растут (постоянная
  амплитуда).

### 5.2. Откуда берётся характеристическое уравнение

Модель 1.6 в однородном виде (без входа):

```
y(t+1) = a1*y(t) + a2*y(t-1) + a3*y(t-2)
```

Ищем решение в виде `y(t) = z^t`. Подставляем и делим на `z^(t-2)`:

```
z^3 = a1*z^2 + a2*z + a3   →   z^3 - a1*z^2 - a2*z - a3 = 0
```

Это и есть **характеристическое уравнение** (степень 3 = порядок системы).
Именно так его формирует `characteristicPolynomial1_6`:

```cpp
return { -a3, -a2, -a1, 1.0 };   // коэффициенты по возрастанию степени z
```

### 5.3. Правило корней (главный критерий)

Общее решение — комбинация членов `C_i * z_i^t`. Тогда:

* если **все** `|z_i| < 1`, то `z_i^t → 0` — система **устойчива**;
* если **хотя бы один** `|z_i| > 1`, то соответствующий член растёт —
  система **неустойчива**;
* если **максимальный** `|z|` **равен** 1 — **граница устойчивости** (marginal):
  колебания не затухают.

Число `max |z_i|` называется **спектральным радиусом**. Для устойчивости
требуется `спектральный радиус < 1`.

Геометрическая картинка — **Z-плоскость** (комплексная плоскость): рисуем
единичный круг. Устойчивость = **все корни строго внутри единичного круга**.

### 5.4. Критерий Шура

Искать корни — долго и не всегда нужно. **Критерий Шура** — это
**алгебраический** критерий: он говорит «устойчиво / нет», работая только с
коэффициентами полинома, без вычисления корней. Идея: полином устойчив ⟺
`|a0| < |an|` (свободный член по модулю меньше старшего), после чего
применяется **рекурсия Шура** — строится полином меньшей степени:

```
q_k = (an*p_k - a0*p_{n-k}) / (an^2 - a0^2),  k = 1..n
```

и процедура повторяется, пока степень не дойдёт до 1.

В коде `schurVerdict`:

```cpp
if (absA0 > absAn + eps) return Unstable;        // |a0| > |an| — сразу неустойчиво
if (abs(absA0 - absAn) <= eps) onBoundary = true;// |a0| = |an| — корень на |z| = 1
if (!(denominator > 0.0))                        // an^2 - a0^2 <= 0
    return onBoundary ? Marginal : Unstable;
… строим q и уменьшаем степень …
```

* `eps = 1e-12 * max(1.0, |an|)` — допуск для сравнения чисел с плавающей
  точкой (точного равенства в double не бывает).
* Если по ходу хоть раз встретилось `|a0| = |an|` (корень на единичной
  окружности) — итог `Marginal`, иначе `Stable`.
* Возвраты: `Stable` (устойчиво), `Unstable` (неустойчиво), `Marginal` (граница).

### 5.5. Применение к модели 1.6

`analyzeModel1_6(a1,a2,a3)`:

1. строит полином `{-a3, -a2, -a1, 1}`;
2. находит корни (`findRoots`) и считает спектральный радиус `max |z|`;
3. выносит вердикт критерием Шура (`schurVerdict`);
4. складывает всё в `StabilityReport`.

`needsWarning(report)` возвращает `true`, если вердикт **не** `Stable` —
программа обязана предупредить пользователя, что результаты симуляции на
неустойчивой модели бессмысленны.

Пример (из отчёта ЛР №3): `a1=0.4, a2=0.3, a3=0.1` → характеристическое
уравнение `z^3 - 0.4z^2 - 0.3z - 0.1 = 0` → корни `0.874`, `-0.237 ± 0.241i`
→ все внутри круга → `|z|max = 0.874` → **STABLE**.

## 7. ЛР №3: теория

### 7.1. Задача управления

Есть объект (например, нагреватель) с выходом `y` (температура). Нужно, чтобы
`y` вышла на задание `w` (уставку) и удерживалась. Управление разомкнутой
системой ненадёжно: помехи и неточности модели уводят выход. Поэтому строят
**замкнутую систему**: регулятор смотрит на **ошибку** и корректирует вход.

```
      w (уставка)                                             
          │      e = w - y                                     
          ▼   ┌──────────┐   u   ┌────────────┐   y            
          ●──►│   ПИД    │──────►│   ОБЪЕКТ   │───┬──►          
          ▲   └──────────┘       └────────────┘   │            
          │                                        │            
          └────────────────────────────────────────┘  обратная связь
```

Ошибка `e(t) = w − y(t)`. Регулятор вырабатывает управление `u` так, чтобы
уменьшить ошибку.

### 7.2. ПИД-закон в непрерывном виде

```
u(t) = Kp*e + Ki*∫e dt + Kd*de/dt
```

* **П** (пропорциональная, `Kp`) — реакция на текущую ошибку. Больше `Kp` →
  быстрее, но возможен «перелёт» (перерегулирование).
* **И** (интегральная, `Ki`) — накапливает ошибку. Именно она убирает
  **статическую ошибку** (остаточную ошибку в установившемся режиме), которую
  П-регулятор оставить не может.
* **Д** (дифференциальная, `Kd`) — реагирует на **скорость** изменения ошибки,
  «притормаживает» заранее → уменьшает перерегулирование.

### 7.3. Рекуррентная (инкрементная) форма, или «алгоритм скорости»

В методичке используется дискретная форма, где считается **приращение**
управления:

```
Δu(τ) = Kp*(e(τ) - e(τ-1)) + Ki*e(τ)*Δt + (Kd/Δt)*(e(τ) - 2e(τ-1) + e(τ-2))
u(τ)  = u(τ-1) + Δu(τ)        с обрезкой  u ∈ [uMin, uMax]
```

Смысл каждого слагаемого:

* `Kp*(e - e_prev1)` — П-канал в приращениях (реакция на **изменение** ошибки);
* `Ki*e*dt` — И-канал (ошибка, накопленная за такт);
* `(Kd/dt)*(e - 2e_prev1 + e_prev2)` — Д-канал (вторая разность = аналог
  второй производной, аппроксимация скорости);

Память регулятора — три числа: `u_prev = u(τ-1)`, `e_prev1 = e(τ-1)`,
`e_prev2 = e(τ-2)`. В конце такта история сдвигается.

**Обрезка `u` в `[uMin, uMax]`** — это физическое ограничение актуатора
(например, мощность нагревателя не может быть больше 100%). Она же играет роль
простейшего **anti-windup**: не даёт интегратору «наматывать» значение, которое
актуатор всё равно не может выдать.

### 7.4. Статический коэффициент усиления и контрольная точка

Для линейной модели 1.6 установившийся выход при постоянном `u`:

```
y* = g * u*,   где   g = b / (1 - a1 - a2 - a3)
```

Значит, для задания `w` установившееся управление `u* = w / g`. Это
**контрольная точка** проверки: если регулятор сошёлся, то `u` в конце должно
быть равно `w/g`. Пример: `a1=0.4, a2=0.3, a3=0.1, b=1` → `g = 1/0.2 = 5`;
для `w=10` → `u* = 2`, для `w=30` → `u* = 6`.

### 7.5. Почему П-регулятор оставляет ошибку, а И — убирает

П-регулятор даёт `u = Kp*e`. В равновесии нужен конкретный `u* = w/g`, но
`u = Kp*e` при `e=0` даёт нулевое управление — противоречие. Отсюда остаточная
ошибка:

```
e* = w / (1 + Kp*g)
```

Пример (из отчёта): `Kp=0.5, g=5, w=10` → `e* = 10/3.5 ≈ 2.857`. Интегральный
канал накапливает ошибку и «дожимает» выход до `w`, устраняя `e*` ценой
увеличения перерегулирования. Д-канал затем уменьшает перерегулирование.

### 7.6. Два режима работы (требование задания)

* **Режим А** — фиксированное число тактов `n`: просто крутим цикл `n` раз.
* **Режим Б** — до установления: крутим, пока `|e| < ε` (с предохранительным
  лимитом `n = 100000`, чтобы не зациклиться, если система не сходится).

### 7.7. Объекты управления

Объект выбирается из меню: любая из трёх моделей ЛР №1 (1.6 — линейная,
2.8 — нелинейная, 3.10 — дифференциальное уравнение). Для линейной 1.6 перед
стартом считается устойчивость (модуль из ЛР №2): если набор коэффициентов
неустойчив, программа предупреждает и спрашивает `Y/N`.

## 9. ЛР №3: разбор кода

### 9.1. `src/PIDController.h` (новый, главный файл работы)

```cpp
class PIDController
{
private:
    double Kp, Ki, Kd;          // коэффициенты
    double dt;                  // шаг квантования
    double uMin, uMax;          // пределы актуатора
    double u_prev  = 0;         // u(t-1)  — память регулятора
    double e_prev1 = 0;         // e(t-1)
    double e_prev2 = 0;         // e(t-2)
public:
    PIDController(double Kp, double Ki, double Kd, double dt, double uMin, double uMax)
        : Kp(Kp), Ki(Ki), Kd(Kd), dt(dt), uMin(uMin), uMax(uMax) {}

    double step(double w, double y)
    {
        const double e = w - y;                                   // ошибка
        const double dU = Kp * (e - e_prev1)                      // П в приращениях
                        + Ki * e * dt                             // И
                        + (Kd / dt) * (e - 2.0 * e_prev1 + e_prev2); // Д (вторая разность)
        double u = u_prev + dU;                                   // инкрементная форма
        if (u > uMax) u = uMax;                                   // обрезка сверху
        else if (u < uMin) u = uMin;                              // обрезка снизу
        e_prev2 = e_prev1;                                        // сдвиг истории
        e_prev1 = e;
        u_prev = u;
        return u;
    }

    void reset() { u_prev = e_prev1 = e_prev2 = 0; }              // обнуление памяти
};
```

Построчно:

* `e = w - y` — ошибка «задание минус выход».
* `dU` — приращение управления; ровно формула из раздела 7.3.
* `u = u_prev + dU` — новое управление = предыдущее + приращение.
* `if (u > uMax) u = uMax; else if (u < uMin) u = uMin;` — **насыщение**;
  одновременно простейший anti-windup.
* Сдвиг истории **после** обрезки: в память идёт уже реально выданное `u`
  (важно, чтобы антивиндап работал корректно).
* `reset()` — обнуляет память (нужно, например, при перезапуске прогона).

* `createPid` — ввод `Kp, Ki, Kd`, `dt` (должен быть > 0), `uMin < uMax`
  (проверки в цикле).
* `selectMode` — режим 1 (фиксированное `n`) или 2 (до `|e| < eps`, лимит
  `100000`).
* Таблица печатается фиксированной шириной (`std::setw`) — «строго таблицей»
  по требованию задания.

Ключевая функция — `simulate` (замкнутый контур):

```cpp
void simulate(Model& plant, PIDController& pid, double w, int mode, int n,
              double eps, double plantDt, std::ofstream& file)
{
    double y = 0.0, yPrev = 0.0, yPrev2 = 0.0;
    bool reached = false;

    for (int t = 0; t < n; ++t)
    {
        const double e = w - y;                                   // ошибка
        const double u = pid.step(w, y);                          // управление от ПИД
        const double nextY = plant.calculateNext(y, yPrev, yPrev2, u, plantDt); // шаг объекта
        yPrev2 = yPrev; yPrev = y; y = nextY;                     // сдвиг истории объекта

        std::cout << std::setw(5) << t << … w << e << u << y;     // строка таблицы
        file << t << ";" << w << ";" << e << ";" << u << ";" << y << std::endl; // CSV

        if (mode == 2 && std::fabs(e) < eps) {                    // условие остановки (режим Б)
            reached = true;
            std::cout << "Steady state reached: |e| < " << eps
                      << " in " << (t + 1) << " steps." << std::endl;
            break;
        }
    }

    if (mode == 2 && !reached)                                     // не сошлось за лимит
        std::cout << "WARNING: |e| >= " << eps << " within the step limit." << std::endl;
}
```

* Порядок в цикле: сначала регулятор считает `u`, потом объект делает шаг,
  затем сдвигается история объекта. Это и есть замкнутый контур во времени.
* `std::fabs(e) < eps` — критерий установившегося режима; `t+1` — число шагов
  «по-человечески» (нумерация с нуля).
* Если за лимит не сошлось — печатается предупреждение.

Вспомогательные функции ввода:

* `checkInputDouble` — ввод `double` с защитой от некорректного ввода
  (`cin.clear()` + `ignore`, повтор).
* `checkInputInt(text, minVal, maxVal)` — ввод `int` в диапазоне; именно она
  гарантирует, что `switch` в `createPlant` не получит «мусор».

клике). Прогон: `ctest` → 5/5.

### 10.1. `PIDController.MathClampAndReset`

Четыре случая, каждый помечен `SCOPED_TRACE`:

* **Первый такт** (пустая история): `PIDController pid(2.0, 0.5, 0.2, 1.0, -10, 10)`,
  `pid.step(1.0, 0.0)` → ошибка `e = 1`, история нулевая, значит
  `du = 2*1 + 0.5*1 + 0.2*1 = 2.7`. Тест требует ровно `2.7`.
* **Второй такт**: учитывается `e(t-1)`, поэтому результат отличается —
  проверяется `EXPECT_NEAR` с точным эталоном.
* **Обрезка**: при `Kp = 100` и пределах `±5` значение `u` обрезается до `5`, и
  дальше держится на границе (`du = 0`) — прямое доказательство работы
  anti-windup/насыщения.
* **`reset()`**: после сброса памяти повтор первого такта снова даёт `2.7`.

Зачем: это математика ядра регулятора + поведение пределов.

### 10.2. `ClosedLoop.FollowsModel16ReferenceTrajectory`

Проверяет **весь замкнутый контур** «ПИД + модель 1.6» против ручного расчёта:
для объекта `(0.4, 0.3, 0.1, 1.0)` и `PID(0.2, 0.1, 0, dt=1)`, `w=10` первые
четыре такта должны дать `u = {3.0, 3.1, 3.41, 3.461}` и
`y = {3.0, 4.3, 6.03, 7.463}`. Цикл прогоняет контур так же, как `simulate`, и
сравнивает оба ряда. Это эталонный тест «правильности всей связки».

### 10.3. `ClosedLoop.ReachesSetpointWithinEps`

Свойство **сходимости**: те же объект, ПИ-настройка `(0.3, 0.1, 0)`, `w = 10`;
через 200 тактов ошибка должна стать < 0.05 (`EXPECT_NEAR(w - y, 0, 0.05)`).
Зачем: доказывает, что контур действительно выходит на уставку, а не просто
«считает какие-то числа».

### 10.4. `Plants.ReturnKnownValues`

Корректность всех трёх объектов (сравнение со значениями, посчитанными вручную
по формулам) и `getName()` для 1.6. Один укрупнённый тест вместо трёх —
родственные проверки объединены с `SCOPED_TRACE`.

### 10.5. `Stability.LinearModelVerdictsAndReport`

Модуль устойчивости из ЛР №2 в контексте ЛР3:

* устойчивый набор `(0.4, 0.3, 0.1)` → `Stable`, `|z| < 1`, предупреждение не
  нужно, `describe` содержит `STABLE`;
* неустойчивый набор `(2.0, 0, 0)` → `Unstable` (корень `z = 2`), `|z| > 1`,
  предупреждение нужно;
* тривиальные полиномы (степень 0, линейный) → `Stable`.

**Зачем тесты в ЛР №3:** подтвердить (1) математику ПИД-регулятора, (2) работу
замкнутого контура и его сходимость, (3) корректность объектов управления,
(4) вердикты устойчивости — то есть все содержательные части работы.

### 10.6. Как читать вывод тестов

`otis_tests.exe` печатает для каждого теста строку `[ RUN ]`, затем `[ OK ]`,
в конце — итог `[ PASSED ] N tests`. `ctest --output-on-failure` печатает
только итог (`100% tests passed`); подробнее — `ctest -V`. При двойном клике по
`otis_tests.exe` окно не закрывается и ждёт Enter (удобно для скриншотов).

## 12. Поток данных

**ЛР №2 (разомкнутый прогон):**

```
пользователь → createModel() ──► модель (Model*)
             → readSignalType() + амплитуда ──► SignalInputSource
             → анализ устойчивости (только 1.6) ──► StabilityReport → вывод
             → simulate(model, config, input) ──► vector<SimStep> ──► таблица + results.csv
             → plot.py ──► result.png
```

**ЛР №3 (замкнутый контур):**

```
пользователь → createPlant() ──► объект (Model*)
             → createPid()    ──► PIDController
             → w, режим (n или eps)
             ┌────────────────── цикл по тактам ──────────────────┐
             │  u = pid.step(w, y)                                │
             │  y_next = plant.calculateNext(y, …, u, dt)         │
             │  таблица t/w/e/u/y → pid_result.csv                │
             └────────────────────────────────────────────────────┘
             → plot.py ──► graph.png
```

Общий принцип обеих работ: **математика отделена от ввода-вывода**, а
корректность математики зафиксирована модульными тестами с эталонами,
посчитанными независимо (вручную или в NumPy).
